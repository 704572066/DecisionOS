# 1. 文档目的

本文档定义 DecisionOS
的整体系统架构，说明各核心模块的职责、边界及协作关系。

本文档回答的问题：

> **DecisionOS 内部由哪些核心模块组成？这些模块如何协同工作？**

本文档建立在《004_System_Context》基础之上，不再重复描述系统边界，而是进一步细化系统内部结构。

------------------------------------------------------------------------

# 2. 架构目标

DecisionOS 的架构设计遵循以下目标：

-   高内聚、低耦合
-   AI 原生（AI Native）
-   上下文优先（Context First）
-   可插拔（Pluggable）
-   易扩展（Extensible）
-   易维护（Maintainable）

------------------------------------------------------------------------

# 3. 总体架构

``` text
                    Client
                       │
               API Gateway
                       │
    ┌────────────────────────────────┐
    │                                │
    │       Context Engine           │
    │                                │
    ├────────────────────────────────┤
    │ Knowledge │ Search │ AI │ Workflow │
    └────────────────────────────────┘
                       │
               Infrastructure
```

Context Engine
是平台的编排核心，不负责永久保存业务数据，而是负责组织上下文、协调各能力模块。

------------------------------------------------------------------------

# 4. 核心模块

## 4.1 Client

职责：

-   Web 应用
-   Desktop 客户端
-   用户交互
-   数据展示

Client 不承担业务逻辑。

------------------------------------------------------------------------

## 4.2 API Gateway

职责：

-   请求入口
-   身份认证
-   权限校验
-   请求路由
-   限流

所有客户端请求统一经过 API Gateway。

------------------------------------------------------------------------

## 4.3 Context Engine

职责：

-   聚合上下文
-   构建上下文
-   管理上下文生命周期
-   协调各业务模块
-   对外提供 Context API

Context Engine 是平台的协调者（Orchestrator），而不是业务数据拥有者。

------------------------------------------------------------------------

## 4.4 Knowledge Service

职责：

-   企业知识管理
-   文档管理
-   知识关联
-   知识索引
-   知识生命周期管理

Knowledge Service 是事实（Facts）的来源。

------------------------------------------------------------------------

## 4.5 Search Service

职责：

-   全文检索
-   向量检索
-   语义检索
-   Context 检索
-   Evidence 检索

Search Service 不直接维护知识数据。

------------------------------------------------------------------------

## 4.6 AI Service

职责：

-   Prompt 管理
-   Tool Calling
-   Model Routing
-   AI 推理
-   建议生成

AI Service 不负责企业知识存储。

------------------------------------------------------------------------

## 4.7 Workflow Service

职责：

-   工作流协调
-   Meeting Flow
-   Decision Flow
-   长事务管理

Workflow Service 编排业务流程，不拥有业务数据。

------------------------------------------------------------------------

# 5. 模块协作关系

``` mermaid
flowchart LR

Client --> Gateway

Gateway --> Context
Gateway --> Knowledge
Gateway --> Search
Gateway --> AI
Gateway --> Workflow

Context --> Knowledge
Context --> Search
Context --> AI
Context --> Workflow

AI --> Search
AI --> Knowledge
Workflow --> Context
```

所有模块通过公开接口通信，避免直接依赖内部实现。

------------------------------------------------------------------------

# 6. 数据流

典型处理流程如下：

1.  用户通过 Client 发起请求。
2.  API Gateway 完成认证和路由。
3.  Context Engine 根据请求组织上下文。
4.  Search Service 检索相关内容。
5.  Knowledge Service 返回事实数据。
6.  AI Service 完成分析与推理。
7.  Context Engine 聚合最终结果。
8.  返回客户端展示。

------------------------------------------------------------------------

# 7. 横向能力（Cross-Cutting Concerns）

所有模块共享以下平台能力：

-   Authentication
-   Authorization
-   Logging
-   Monitoring
-   Configuration
-   Audit
-   Event Bus

这些能力属于平台基础设施，不属于具体业务模块。

------------------------------------------------------------------------

# 8. 架构原则

## Context First

上下文是平台核心资产。

## Evidence Driven

AI 输出必须能够关联证据。

## Human in Control

AI 提供建议，人负责最终决策。

## Loose Coupling

模块之间通过稳定接口通信。

## Pluggable AI

支持替换不同 AI Provider。

## Vendor Neutral

不依赖单一厂商或云平台。
